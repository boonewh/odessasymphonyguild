## October 5: durable staff login limits

- Five admissions per trimmed/lowercase email in a fixed 15-minute window; 120 total admissions in a fixed five-minute window. A locked global row serializes parallel requests, with database time sampled after acquiring the lock. Successful authentication still consumes an admission. Denials neither increment counters nor extend their deadline; restarting the app does not clear counters.
- Email buckets are HMAC-SHA256 values using the existing server-only development token. Counters contain no raw email, password or IP address. Expired email counters are removed lazily by a subsequent request when the global limit permits processing. This cleanup is not an approved contact-data retention policy.
- RLS/private grants prevent anonymous and authenticated browser roles from reading/writing counters or executing the admission RPC; only the server service role is allowed. Missing, unavailable or malformed limit responses fail closed with 503 and `Retry-After: 60`, before Auth is called. Throttled requests return 429 with a positive `Retry-After`; the form shows the remaining wait rounded up to minutes.

GET session checks and DELETE logout do not consume attempts. Forwarded IP headers are not trusted or used to allocate budgets. The stream has a byte bound, not a new request-body time deadline.
